## Architecture decision

Keep the established Python miner, FastAPI HTTP API, Socket.IO transport, local persistence, and Docker runtime. Replace the hand-written HTML/JavaScript/CSS dashboard with a strict TypeScript React application. Python remains responsible for mining decisions, credentials, persistence, and access control. React owns presentation, navigation, forms, and browser state.

The existing frontend has about 3,000 lines of application JavaScript and 1,900 lines of styling, plus separate authentication assets. The redesign replaces these together, including login and maintenance flows. Existing source in `src/models`, `src/services`, `src/auth`, `src/api`, and `src/websocket` remains the behavioral reference.

A backend language migration would add risk without improving the requested interface. Limited backend changes are appropriate where the new interface needs accurate progress metadata, consistent snapshots, bounded history responses, or static asset serving; each needs a focused regression test.

## Proposed stack

| Concern | Choice | Reason |
| --- | --- | --- |
| Miner/runtime | Existing Python 3.12+, FastAPI, Pydantic, python-socketio, uv lockfile | Preserve proven behavior and deployment model |
| Browser application | React 19 with TypeScript in strict mode | Component-based complete frontend rewrite |
| Build | Vite 8; Node 24 LTS for development/build only | Fast local development and hashed production assets |
| Styling | Tailwind CSS 4 through its Vite plugin | Shared CSS theme tokens and compact utility styling |
| Icons | Individual `@mdi/js` SVG paths | User-requested MDI without an entire icon font |
| Navigation | React Router, declarative browser routes | Direct links, back/forward, five simple screens |
| Live state | Existing Socket.IO client plus one typed React state provider | Reuse existing events; one connection and one authoritative snapshot |
| HTTP | Small typed wrapper around native fetch | Shared CSRF header, error handling, session expiry, and cancellation |
| Forms | Native form controls and local React state | Accessible, consistent inputs without a form framework |
| Data | Existing settings, cookies, authentication, and history files | No database or account migration required |
| Validation | Existing pytest/Ruff/Mypy plus TypeScript, focused frontend tests, Playwright | Preserve backend checks and replace obsolete DOM-source tests |
| Distribution | Multi-stage Docker build; Python serves compiled frontend | One container, one port, no Node service in production |

Use the latest mutually compatible patches when installing and commit the lockfile. Recommendations checked against [React releases](https://react.dev/versions), [Node release support](https://nodejs.org/en/about/previous-releases), [Vite](https://vite.dev/guide/), [Tailwind's Vite integration](https://tailwindcss.com/docs/installation/using-vite), and [MDI documentation](https://pictogrammers.com/docs/library/mdi/getting-started/react/).

Keep one frontend package and the existing Python package. A single state provider handles live entities; forms remain local and never overwrite a dirty draft on an unrelated socket event. Ordinary page/filter state belongs in the URL when it should survive navigation. Add a query/store library only if a concrete requirement outgrows this structure.

## Design and layout

The detailed [design specification](./2026-09-26-design-spec.md) defines tokens, controls, wireframes, each screen, responsive layouts, accessibility, and review states.

- Fixed dark appearance: charcoal canvas, flat neutral surfaces, quiet separators, Manrope, 4px field corners.
- Overview prioritizes current reward and progress, then queue and channels. The existing large login/log panels move into contextual flows.
- Campaigns uses orderly expandable rows with filters and compact artwork; History records confirmed claims; Activity contains diagnostics; Settings uses clearly labeled groups.
- Fields match OhneGuessr's 36px geometry, padding, dark fill, inset search icon, and consistent select/numeric controls. Focus and required control outlines stay visible.
- Custom scrollbars match the reference: 3px in Chromium/WebKit, transparent tracks, rounded neutral thumbs, hidden arrow buttons; Firefox uses `scrollbar-width: thin`. Native wheel/touch/keyboard scrolling remains intact.
- No emojis or saturated decorative accents. Status relies on text and MDI icons. Game/reward thumbnails remain recognizable content.

## Data flow and contracts

1. Load dashboard auth status through its public endpoint. If required, show the new login route before loading protected data or opening the live connection.
2. After authorization, connect once to Socket.IO. Receive the existing complete initial snapshot, hydrate the provider, and then apply incremental events. React StrictMode cleanup must not leave duplicate listeners.
3. A reconnect discards assumptions about missed events and hydrates a fresh complete snapshot. Mark old data stale until this completes. Preserve unsaved form drafts separately.
4. Commands use HTTP and the existing `X-TDM-Request: 1` header. Show success only after the server accepts the action; never queue state-changing commands for later automatic retry.
5. HTTP 401/session revocation closes the connection, clears protected in-memory data, and returns to dashboard login. Realtime authorization remains enforced by Python at connect, event, broadcast, and expiry.
6. Keep frontend DTO types beside the API/state helpers, supported by fixture-based contract tests. Add response models when touching an API boundary rather than refactoring unrelated backend routes.
7. Keep translated UI strings out of raw HTML. Validate external links and use React's normal escaped rendering. Secrets must never enter browser storage, logs, exported fixtures, screenshots, or committed artifacts.
8. Reuse the existing finite console buffer and bound the browser's activity list. History pagination should preserve API filtering/export semantics and disclose any result limit.

## Login and upstream compatibility

Dashboard password and Twitch authentication are separate flows. Restyle both consistently, but preserve the existing supported authentication mechanism. Do not add a fake OAuth callback, request new permissions, or collect a Twitch password for a flow that cannot use it.

As checked on 25 September, upstream tracks fresh-login and campaign-access restrictions separately from the UI rewrite. A redesigned page is not evidence that those restrictions are resolved. The interface must distinguish restricted/failed campaign access from an actually empty inventory. Any browser-helper integration or changed Twitch login strategy needs its own verified work; it is not silently included in the redesign. [Upstream tracking issue #118](https://github.com/rangermix/TwitchDropsMiner/issues/118).

Offline fixtures and mocked tests can establish UI and API behavior, not live Twitch progress. This task does not authorize access to the user's Pi/server. Any live account verification must be explicitly arranged separately.

## Persistence, rollback, and scope

Existing Python storage remains authoritative. Do not import or rewrite cookies, auth files, history, proxy credentials, or Telegram credentials as part of this frontend migration. The fixed-dark UI can ignore the old theme preference without destroying it. Preserve backwards-compatible defaults if additional display metadata is introduced.

Keep the previous Git revision and deployment image available for rollback. A future deployment can switch images while retaining the same data volume; backup and live deployment require a separate authorized task. A build/startup failure must not erase data or disable dashboard protection.

This implementation does not expand mining into multiple accounts, parallel claimed-progress promises, channel points, unlinked campaigns, or a hosted service. It completes the requested interface rewrite around existing supported behavior.
